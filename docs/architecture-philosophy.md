# 数值 vs LLM：谁主谁辅？

**日期**: 2026-06-08
**版本**: 1.0
**作者**: Prometheus (Hermes Agent)
**状态**: 草案

---

## 问题

在混合模拟引擎中，数值仿真和 LLM 推理，谁为主，谁为辅？

两个极端：
- **《三国志》模式**: 数值为主。每个行为有公式。玩家看数字做决策。LLM 可有可无。
- **《崇祯模拟器》模式**: LLM 为主。一切由 AI 生成。数值是装饰。55% 好评。

我们走哪条？

---

## 答案：分层共治，不分主辅

**引擎和 LLM 不是竞争关系。它们服务不同的需求。**

```
        玩家体验
       ╱        ╲
   沉浸感          公平感
   (LLM 提供)     (引擎保证)
```

一个只有公平没有沉浸的游戏 = 电子表格（纯 ROTK）
一个只有沉浸没有公平的游戏 = 聊天机器人（纯崇祯）

**好游戏需要两者。**

---

## 三层模型

```
┌─────────────────────────────────────────┐
│  Layer 3: 表达层 (LLM)                  │
│  「曹孟德亲率虎豹骑，旌旗蔽日…」         │
│  负责: 沉浸感、叙事、情感共鸣            │
│  可以错: 修辞夸张、细节想象              │
├─────────────────────────────────────────┤
│  Layer 2: 理解层 (LLM)                  │
│  「围魏救赵」→ {attack:宛城, strategy:牵制} │
│  负责: 意图解析、上下文理解              │
│  可以模糊: 多义性、策略推断              │
├─────────────────────────────────────────┤
│  Layer 1: 计算层 (Engine)               │
│  兰彻斯特方程、对数发展公式、A*寻路       │
│  负责: 公平性、可复现性、正确性           │
│  不能错: 战斗结果、经济产出、NPC行为      │
└─────────────────────────────────────────┘
```

**Layer 1 不能错。Layer 2 可以模糊。Layer 3 可以夸张。**

这不是谁主谁辅——这是**分层问责**。

---

## 引擎是地基，LLM 是装修

> 你可以没有装修住进毛坯房（ROTK 模式 — 能玩）。
> 你不能没有地基住进空中楼阁（崇祯模式 — 55% 好评）。

**引擎不是「为主」——引擎是「为底」。**

《三国志》系列 40 年证明了：纯数值可以做出好游戏。
《崇祯模拟器》1 个月证明了：纯 LLM 做不出好游戏。

所以我们的选择不是「谁主谁辅」——是**用 LLM 把引擎的好体验放大 10 倍**，而不是**用 LLM 替代引擎**。

---

## 具体边界

| 场景 | 谁负责 | 为什么 |
|------|--------|--------|
| 「进攻宛城」→ 战斗结算 | **引擎** | 必须公平。玩家 A 和玩家 B 打同一仗，结果应该一样 |
| 战斗结果 → 叙事文本 | **LLM** | 「decisive_victory, casualties=651」→ 需要变成生动的故事 |
| 「围魏救赵，联孙权牵制曹操」| **LLM→引擎** | LLM 理解成 multi-step strategy，引擎验证可行性 |
| NPC 是否进攻你 | **引擎** | 曹操 aggression=0.8，你的边境兵力 < 他的 60% → 进攻 |
| NPC 进攻的理由 | **LLM** | 「丞相料定刘表新得十城，根基未稳…」 |
| 开发宛城需要多少金 | **引擎** | `150 × 10 × √(50000/1000)` = 公式计算 |
| 合法性 +20 意味着什么 | **LLM** | 「天下士人闻公克复洛阳，纷纷来投…」 |

**规则引擎**: 凡是涉及「多少」「是否」「能不能」的问题，引擎回答。
**叙事引擎**: 凡是涉及「为什么」「感觉如何」「意味着什么」的问题，LLM 回答。

---

## 一个反直觉的结论

**LLM 的角色越大，引擎的稳定性越重要。**

原因：LLM 的叙事能力是放大器。如果你的引擎结果是对的，LLM 把好的体验放大 10 倍。如果你的引擎结果是错的，LLM 把坏的体验放大 10 倍。

崇祯模拟器的问题不是「用了太多 LLM」——是「引擎根本不存在」。LLM 生成的内容没有事实锚点，所以越写越飘。

**LLM 是乘法器，不是加法器。引擎是底数。**

```
好引擎 × 好 LLM = 神作 (100 × 10 = 1000)
好引擎 × 差 LLM = 能玩 (100 × 1 = 100)  ← ROTK
差引擎 × 好 LLM = 灾难 (1 × 10 = 10)     ← 崇祯
无引擎 × 好 LLM = 聊天机器人 (0 × 10 = 0)
```

---

## 我们的定位

```
《三国志》系列 ──────── 我们 ──────── 《崇祯模拟器》
数值 100%                            LLM 100%
「电子表格」        「历史世界」        「聊天机器人」

我们在中间。但偏向数值侧。
因为我们有崇祯的前车之鉴。
```

**一句话**: 引擎保证这个世界的物理定律是真实的。LLM 保证你在这个世界里的体验是生动的。

---

## 对 SimPly v2 的启示

这个分析直接支持了 v2 的「规则即数据」架构：

- **引擎核心不变**（Hard Engine — 寻路、状态管理、回合循环）
- **规则可配置**（Soft Rules — 战斗参数、经济公式、合法性阈值）
- **LLM 管两头**（理解玩家意图 + 生成叙事）
- **规则市场**让社区定义「这个世界怎么运转」

如果社区想做一个「LLM 为主的崇祯模式」——他们可以。调高 LLM 权重，降低引擎精度。那是他们的规则集。不在主分支。在我们的规则市场上卖。

---

## 结论

**不问「谁主谁辅」。问「什么不能错」。**

不能错的 → 引擎。
可以模糊的 → LLM。
可以夸张的 → LLM。
社区想改的 → YAML。

这就是 SimPly。
