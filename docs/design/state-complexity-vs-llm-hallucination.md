# 游戏状态变量复杂度 vs LLM 幻觉 — 设计决策

> 版本: 0.1 | 2026-06-14
> 状态: 提案 — 待评审
> 相关任务: H15e (人口"?"异常), H15f (本设计)

---

## 一、问题陈述

### 1.1 观察到的现象

在 V1 纯 LLM 引擎的实际运行中（room d4a512fb），孙权势力 Q2 人口显示为"十八万三千"（183,000），而江东在 207 年的实际人口应约 200 万（含编户齐民）。这一异常的根因已通过 H15e 修复（`population` 字段未传递），但暴露了一个更深层的问题：

**LLM 在处理多个精确数值变量时容易产生幻觉、累积误差和不一致。**

### 1.2 核心矛盾

| 维度 | 理想状态 | LLM 现实 |
|------|---------|---------|
| 变量数量 | 越多越真实（人口、兵力、粮草、库金、民心、税率、科技…） | LLM 上下文越复杂，幻觉概率越高 |
| 数值精度 | 精确到个位数（兵力 145,382） | LLM 不擅长精确算术，四舍五入、符号错误频发 |
| 一致性 | 跨回合自洽（Q1 的人口增长应等于出生-死亡+迁移） | LLM 缺乏全局状态追踪，跨回合漂移 |

**这不是模型能力问题，而是架构匹配问题。** GPT-4 / DeepSeek-V4 是语言模型，不是数值模拟器。让 LLM 同时担任"数值引擎"和"叙事引擎"违反了关注点分离原则。

## 二、同类游戏调研：宏观指标的抽象方法

### 2.1 Crusader Kings 3 (CK3) — 角色驱动的层级抽象

```
┌─────────────────────────────────────────────────┐
│                 CK3 状态模型                      │
├─────────────────────────────────────────────────┤
│                                                   │
│  角色属性 (Character Stats)                       │
│  ├─ 军事 (Martial)     → 征召兵数量 + 战斗加成     │
│  ├─ 管理 (Stewardship) → 税收 + 领地上限           │
│  ├─ 外交 (Diplomacy)   → 好感度变化速度            │
│  └─ 谋略 (Intrigue)    → 阴谋成功概率              │
│                                                   │
│  领地 (Holdings)                                  │
│  ├─ 发展度 (Development): 0-100 的单一指标        │
│  │   └─ 决定税收基数 + 征召兵基数 + 补给上限      │
│  ├─ 控制力 (Control): 0-100                       │
│  └─ 建筑 (Buildings): 提供固定加成 (如 +200 征召兵)│
│                                                   │
│  军事                                              │
│  ├─ 征召兵 (Levies): 从领地自动生成               │
│  │   = Σ(发展度 × 建筑系数 × 角色军事加成)        │
│  └─ 常备军 (Men-at-Arms): 职业兵种，玩家手动招募  │
│                                                   │
│  ✦ 关键设计: 没有"人口"这一独立变量               │
│     人口被吸收进"发展度"+"控制力"两个维度          │
│     LLM 只需判断"发展度高/低"而非"人口 183,421"    │
└─────────────────────────────────────────────────┘
```

**对 histrategy 的启示：**
- CK3 用 0-100 的连续指标代替离散人口数，避免了数值漂移
- 征召兵是**派生值**，不是独立变量 — (发展度 × 系数) 自动计算，不会出现"增兵但人口不变"的矛盾
- 角色属性（军事/管理）作为**乘数**而非直接加减，保持比例关系稳定

### 2.2 Total War: Three Kingdoms — 单位驱动的离散模型

```
┌─────────────────────────────────────────────────┐
│           Total War: 3K 状态模型                 │
├─────────────────────────────────────────────────┤
│                                                   │
│  城池 (Settlements)                               │
│  ├─ 等级 (Tier 1-10): 城镇 → 大县城 → 都城       │
│  ├─ 人口: 显示为数字，但实际按等级分段            │
│  │   Tier 3: ~180,000 | Tier 5: ~420,000         │
│  └─ 粮食: 全局资源池 (非城池级)                   │
│                                                   │
│  军事                                              │
│  ├─ 部曲 (Retinues): 武将绑定的 6 队单位          │
│  │   每队 = 固定兵力 (如骑兵 60 人/队)            │
│  ├─ 补员率: 由城池人口 + 科技 + 将领技能决定      │
│  └─ 总兵力 = Σ(所有部曲 × 每队人数)              │
│                                                   │
│  ✦ 关键设计: 军事力量 = 武将 × 部曲数             │
│     不是"刘备有 5000 兵"，而是"刘备+关羽+张飞     │
│     各带 2 队步/1 队骑/1 队弓"                   │
│     武将阵亡 → 部曲解散 → 兵力归零                 │
└─────────────────────────────────────────────────┘
```

**对 histrategy 的启示：**
- 武将不应该只是"军师说一句话"，而是兵力的**载体**
- 兵力不应是独立数字，而应与武将/城池绑定（"关羽率 2000 精兵驻新野" 比 "shu: troops=5000" 更不易出错）
- 人口按城池等级分层，减少 LLM 在精确数字上的负担

### 2.3 Civilization VI — 公民驱动的生产力模型

```
┌─────────────────────────────────────────────────┐
│              Civilization VI 状态模型              │
├─────────────────────────────────────────────────┤
│                                                   │
│  人口 = 公民数 (Population = Citizens)             │
│  ├─ 1 公民 = 1 个地块产出                          │
│  ├─ 每个公民消耗 2 粮食/回合                       │
│  └─ 人口增长 = f(剩余粮食, 住房, 宜居度)          │
│                                                   │
│  产出 (Yields)                                    │
│  ├─ 粮食 (Food)     → 人口增长                    │
│  ├─ 生产力 (Production) → 建造速度                │
│  ├─ 金币 (Gold)     → 维护费 + 购买               │
│  ├─ 科技 (Science)  → 科技树进度                  │
│  └─ 文化 (Culture)  → 政策树进度                  │
│                                                   │
│  ✦ 关键设计: 所有变量都是**差分方程**             │
│     ΔP = f(S, H, A)  — 确定性函数                 │
│     人口不是任意数，而是前值 × 增长率              │
│     LLM 只调整增长率参数，不做算术                 │
└─────────────────────────────────────────────────┘
```

**对 histrategy 的启示：**
- 人口应该是**存量 + 增长率**，增长率为 LLM 可操作参数
- "税率从 30% 降到 20%，人口增长率从 2% 升到 4%" 比 "人口+15,000" 更稳定
- 粮食 → 人口 → 税基 → 库金的因果链应由确定性引擎维护，LLM 只调参数

## 三、三款游戏的抽象层级对比

| 游戏 | 人口表示 | 军事表示 | 经济表示 | LLM 友好度 |
|------|---------|---------|---------|-----------|
| **CK3** | 发展度 0-100（无精确人口） | 征召兵（派生值）+ 常备军（固定值） | 税收（发展度 × 系数） | ⭐⭐⭐⭐⭐ 最友好 |
| **Total War** | 城池等级 1-10 + 近似数字 | 部曲 × 每队人数（离散） | 收入/回合（单一数字） | ⭐⭐⭐⭐ 较友好 |
| **Civ VI** | 公民数（整数，1-30+/城） | 单位（每个独立维护） | 生产力/金币/回合 | ⭐⭐⭐ 中等 |
| **histrategy 当前** | 城池精确人口 | 精确兵力 | 精确库金/粮草 | ⭐ 不友好 |

### 3.1 关键规律

1. **越成功的策略游戏，数值变量的独立维度越少。** CK3 只有"发展度"一个宏观指标，其余全是派生。
2. **离散 > 连续。** "3 级城池"比"人口 183,421"更稳健；"2 队骑兵"比"兵力 5000"更不易错。
3. **LLM 调参数，代码算结果。** LLM 决定"税率降低"，代码算出"税收 = 税率 × 人口基数"，互不污染。

## 四、histrategy 当前状态模型分析

### 4.1 当前变量清单 (V1/V3)

```
FactionState (每个势力):
  ├─ population      ← H15e 修复前为动态属性，现在从城池汇总
  ├─ strength_actual (兵力)
  ├─ food            (粮草)
  ├─ treasury        (库金)
  ├─ morale_actual   (民心)
  ├─ tax_rate        (税率)
  ├─ territories     (城池列表)
  └─ policies        (政策 → 效果映射)

Territory (每座城池):
  ├─ population
  ├─ development
  ├─ garrison
  ├─ fertility
  └─ fortification
```

### 4.2 当前问题

| 问题 | 表现 | 根因 |
|------|------|------|
| **变量过多** | LLM 需同时追踪 5+ 个独立数值变量 | 每个变量都是 LLM 的自由参数 |
| **跨变量一致性** | "增兵 5000 但人口不变" | LLM 不理解变量间的约束关系 |
| **跨回合漂移** | Q5 的人口与 Q1 人口无因果关联 | 无确定性基线，纯 LLM 记忆 |
| **精度幻觉** | 183,000 vs 350,000 vs 2,000,000 | LLM 对三国人口缺乏精确知识 |

## 五、提案："等效兵力" + "人口分层" 方案

### 5.1 核心理念

> **让 LLM 做它擅长的（判断方向/幅度），让代码做它擅长的（精确计算/约束检查）。**

将当前 5+ 个独立数值变量聚合成 **2 个主变量 + 派生变量** 的层级结构。

### 5.2 方案一：等效兵力 (Equivalent Military Strength)

#### 概念

将势力军事力量抽象为一个 **等效兵力指数**（0-1000），而非精确兵力数字。

```
等效兵力 = f(常备军, 征召潜力, 武将素质, 城池等级, 科技水平)

其中:
  常备军 (Professional Army): 精确数字，由玩家决策直接控制
  征召潜力 (Mobilization Potential): 派生值，由人口和城池决定
  武将素质 (Commander Quality): 0-100，由该势力所有武将的统率+武力加权
  城池等级 (Settlement Tier): 1-10，决定征召上限
  科技水平 (Tech Level): 0-10，兵种战斗力乘数
```

#### LLM 接口

```json
{
  "faction_military": {
    "cao": {
      "standing_army": 85000,           // ← 精确值，LLM 决定增减
      "mobilization_potential": 420,    // ← 0-1000 指数，LLM 判断"高/低"
      "commander_quality": 85,          // ← 0-100，LLM 判断"强/弱"
      "equivalent_strength": 730,        // ← 派生值: f(85000, 420, 85) = 730
      "assessment": "曹操军容强盛，许昌禁军+青州兵合计八万五千，河北可征调民夫四十万"
    }
  }
}
```

#### 优势

1. **LLM 只需判断趋势**："征召潜力从 420 → 480"（+14%），而不是"调集了 32,000 民兵"
2. **精确数字与指数解耦**：`standing_army` 是确定性的，`equivalent_strength` 是相对排序
3. **跨势力可比**：玩家不需要知道"孙权有 60,000 兵"，只需要知道"孙权等效兵力指数 350，你是 730，碾压之"
4. **减少计算负担**："曹操 vs 孙权 = 730 vs 350" 比 "85,000 + 40,000 征召 vs 60,000 + 20,000 征召" 简单 5 倍

### 5.3 方案二：人口分层 (Population Stratification)

#### 概念

将精确人口数字替换为 **分层标签 + 近似范围**。

```
人口层级 (Population Tier):
  Tier 0: 凋敝  — < 20,000  （如: 新野 15,000）
  Tier 1: 稀少  — 20,000 - 60,000  （如: 江口 30,000）
  Tier 2: 中等  — 60,000 - 150,000 （如: 建业 120,000）
  Tier 3: 殷实  — 150,000 - 400,000 （如: 襄阳 250,000）
  Tier 4: 富庶  — 400,000 - 800,000 （如: 许昌+周边 600,000）
  Tier 5: 鼎盛  — > 800,000  （如: 洛阳 1,000,000）
```

城池人口保持精确值（用于确定性计算），但传递给 LLM 的上下文使用分层标签。

#### LLM 接口

```json
{
  "faction_population": {
    "cao": {
      "total_population": 2450000,        // ← 代码计算，LLM 不知此精确值
      "population_tier": "富庶",           // ← 分层标签，LLM 看到此
      "population_range": "200万-250万",    // ← 近似范围
      "tax_base": 4250,                    // ← 派生值: 2450000 × 税率 × 系数
      "growth_trend": "缓慢增长 (+1.5%/季)"  // ← LLM 决定的趋势
    }
  }
}
```

#### 优势

1. **天然容忍误差**："富庶" 涵盖 40 万到 80 万 — LLM 说 "人口约 50 万" 和 "人口约 70 万" 都在可接受范围
2. **语义锚定**：LLM 擅长判断"建业是富庶大城"而非"建业有 183,421 人口"
3. **确定性计算在代码侧**：精确的人口增长/税收计算由 Python 完成，LLM 只影响增长率参数

### 5.4 综合方案：双变量模型

```
                    ┌──────────────────────┐
                    │    LLM 操作用户界面     │
                    │  (分层标签 + 指数)      │
                    └──────┬───────────────┘
                           │
            ┌──────────────┼──────────────┐
            ▼              ▼              ▼
     ┌──────────┐  ┌──────────┐  ┌──────────┐
     │ 军事指数  │  │ 人口层级  │  │ 政策效果  │
     │ (0-1000) │  │(Tier0-5) │  │(乘数)    │
     └────┬─────┘  └────┬─────┘  └────┬─────┘
          │             │             │
          └──────┬──────┴──────┬──────┘
                 ▼             ▼
          ┌──────────────────────────┐
          │    确定性计算引擎 (Python) │
          │  - 兵力精确值              │
          │  - 人口精确值              │
          │  - 税收/粮草/库金          │
          │  - 约束验证 (Guardrail)    │
          └──────────────────────────┘
```

#### LLM 输入（简化后）

```json
{
  "factions": {
    "cao": {
      "military": {
        "standing_army": 85000,
        "equivalent_strength": 730,
        "recent_trend": "稳步扩军"
      },
      "population": {
        "tier": "富庶",
        "range": "200万-250万",
        "growth": "+1.5%/季"
      },
      "economy": {
        "treasury": "充足",
        "food": "盈余",
        "tax_burden": "重税 (40%)"
      }
    }
  }
}
```

#### LLM 输出（简化后）

```json
{
  "faction_changes": {
    "cao": {
      "military_delta": {
        "standing_army_change": -3000,
        "equivalent_strength_change": -15,
        "reason": "夏侯惇攻新野战损三千"
      },
      "population_delta": {
        "tier_change": null,
        "growth_rate_change": -0.5,
        "reason": "征兵导致劳动力减少"
      },
      "economy_delta": {
        "treasury_change": -2000,
        "food_change": -1500,
        "reason": "军费开支+南征粮草消耗"
      }
    }
  }
}
```

### 5.5 确定性计算层的职责

```python
def resolve_deltas(faction_state, llm_deltas):
    """
    将 LLM 输出的"变化方向"转换为精确数值。
    
    输入: LLM 判断 ("粮草减少", "兵力损失三千")
    输出: 精确数值 (food: 10000 → 8500, troops: 60000 → 57000)
    """
    # Step 1: 应用 LLM 的兵力变化
    new_troops = faction_state.strength_actual + llm_deltas["standing_army_change"]
    
    # Step 2: 派生计算 (LLM 无法直接操作)
    new_population = faction_state.population * (1 + growth_rate / 100)
    new_food = faction_state.food + food_production - food_consumption(new_troops)
    new_treasury = faction_state.treasury + tax_income - military_upkeep(new_troops)
    
    # Step 3: Guardrail 验证
    assert 5000 <= new_population_per_city  # 每城至少5000人
    assert new_food >= 0                     # 粮草不为负
    assert abs(new_troops - old_troops) / old_troops <= 0.30  # 单季 ≤30%变化
```

## 六、实施路线图

### Phase 1: 最小可行改进（H15e 已完成的基础上）

1. ✅ **H15e**: 修复 `population` 字段传递（从城池汇总）
2. **本提案 H15f**: 在 `_build_context()` 中同时输出精确值和分层标签

### Phase 2: 分层上下文（1 天）

- 在 `_build_context()` 中添加 `population_tier` 和 `equivalent_strength` 的计算
- 修改 `v1_simulator.md` 系统提示词，引导 LLM 使用分层坐标而非精确数字
- 保留精确值在 context 中（作为参考），但叙事和决策引导使用分层

### Phase 3: 派生变量引擎（2-3 天）

- 实现 `resolve_deltas()` 确定性计算层
- 将 V1 的输出后处理从 "直接接受 LLM 数值" 改为 "LLM 趋势 + 代码计算精确值"
- 添加跨变量一致性检查（增兵必消耗人口/粮草/库金）

### Phase 4: A/B 对比（1 天）

- 同一场景分别跑"精确数字模式"和"分层模式"
- 对比：叙事质量、数值一致性、玩家理解度
- 用户决策：采用分层模式 or 保留精确数字

## 七、风险与权衡

| 风险 | 缓解措施 |
|------|---------|
| 分层过于粗糙，失去三国写实感 | 保留精确值在后台，界面可切换"详细/简洁"模式 |
| 等效兵力指数让玩家感受不到"我有 85000 兵"的成就感 | 常备军（standing_army）保持精确数字，等效指数是辅助排序 |
| 增加代码复杂度，V1 的"纯 LLM 哲学"被稀释 | 这是有意的哲学转变：LLM 是决策引擎，代码是计算引擎 |
| CK3/Total War 模式在此适用性存疑 | Phase 4 的 A/B 对比会给出数据驱动答案 |
