# 我放弃了让大模型当游戏引擎，转而写了 239 个单元测试

> 一个开源三国策略游戏的 v2 重构笔记：为什么 LLM 不该当裁判，确定性物理引擎 + AI 叙事才是正解。

---

今年 5 月，我开始做一个实验：能不能让 DeepSeek 当三国游戏的主宰——它生成谋臣建言、模拟两军对垒、推演天下大势。玩家只需要像发微信一样输入自然语言。

这是我设想的「AI native 游戏」：没有菜单、没有按钮、没有血条。玩家说的话就是物理定律。

第一版很快就跑起来了。它甚至能生成漂亮的文言叙事：

> 「建安十二年冬，曹操坐拥中原九郡，带甲十五万……」

但玩到第三回合，问题就暴露了。

## 为什么 LLM 是糟糕的游戏裁判

1. **幻觉注入**：玩家随口说「今年风调雨顺」，LLM 可能当真，凭空给粮食产量加 30%。你可以用话术骗过裁判。

2. **偏向玩家**：LLM 知道谁是「用户」，天然倾向让玩家的决策成功。我测试时发现，同样兵力对比下，玩家方的胜率比 NPC 方高出 20-30%。

3. **不可复现**：同样的输入产生不同的输出。无法写测试、无法做平衡、无法回答「这个机制到底对不对」——因为每次答案都不一样。

这就像让一个口才极好但不懂数学的人去当足球裁判。场面很好看，但比分不靠谱。

而且更致命的是——**一旦玩家发现可以「话术骗过裁判」，游戏的策略深度就归零了。**

## 转折：把裁判换成计算器

于是我推翻了整个 v1，重新定义了 v2 的架构：

```
确定性物理引擎（零 LLM）
    ↓ 计算出结果：谁赢了、死了多少人、粮草还剩多少
LLM 叙事引擎（只读，不修改状态）
    ↓ 把结果翻译成文言故事
玩家看到的历史叙事
```

**核心原则很简单：LLM 只能看，不能改。**

具体来说，我借鉴了光荣《三国志》30 年的设计经验，把游戏拆成了七个独立引擎——前六个是纯 Python 确定性计算，第七个才是 LLM：

| 引擎 | 职责 | 核心技术 |
|------|------|----------|
| Map Engine | 地形、关隘、补给线 | A\* 寻路、地形修正 |
| Character Engine | 武将五维、忠诚度、自然死亡 | 概率模型 |
| Domestic Engine | 粮食生产、人口增长、税收 | YAML 公式驱动 |
| Military Engine | 兵种相克、战斗结算、补给消耗 | 兰彻斯特方程 |
| Decision Engine | NPC 行为（曹操 aggression=0.8，刘备 mercy=0.95） | 权重决策树 |
| History Engine | 历史事件触发、蝴蝶效应 | 条件触发 × 引力系数 |
| **Narrative Engine** | 生成文言叙事 | **LLM · 只读** |

NPC 的输出格式和玩家命令完全一致——`Command(type="attack", params={...})`。物理引擎不知道谁是 NPC 谁是人类。**这就是公平性：裁判不认识运动员。**

## 现在能玩什么？

首发剧本是 207 年「三顾茅庐→白帝托孤」——三国最知名的一段。可选刘备（5000 兵守新野一城，绝境求生）、曹操（15 万大军横扫中原）、孙权（6 万水军坐断东南）。

玩法是这样的。你输入：

> 「从宛城出兵进攻新野的刘备，他只有 5000 兵。同时在下邳部署 3 万兵力防守，防范孙权偷袭。」

系统先解析你的意图（用一个小型 LLM 做结构化提取），然后确定性引擎计算行军速度、粮草消耗、战斗结果、NPC 反应，最后用大模型生成一段文言叙事告诉你发生了什么。

没有「你赢了」的弹窗，只有一段像《资治通鉴》一样的文字。

已经有真实玩家玩到第 19 回合了。一个选孙权的玩家，先稳固江东经济、再与刘备结盟、趁曹操主力被牵制时南征长沙——每一步都有策略深度，每一步的结果都由引擎决定，不是 AI 编的。

## 为什么花了 239 个测试

因为确定性引擎的每一个模块都可以单独测试。气候系统用 `sha256(territory:year:season:turn)` 做 seeded RNG，战斗结算用兰彻斯特方程，忠诚度变化用合法性 × 相性。这些都是纯数学——写一个测试，它就永远是绿的。

同样重要的是，玩家说的「风调雨顺」四个字在系统里找不到任何匹配命令——直接丢弃，不影响游戏状态。这样既保留了自然语言输入的自由度，又防止了 LLM 幻觉注入。

## 一个你可能会觉得有意思的想法

这个项目的规则引擎（战斗公式、经济模型、事件触发条件）全部是 **YAML 配置**，不在代码里。

```
# economy.yaml
food_consumption_per_soldier: 1.0
winter_multiplier: 1.5
tax_cap: 0.5
morale_decay_per_tax_point: 2
```

这意味着你不需要会 Python 也能参与游戏设计。改一个数字，平衡性就变了。我们把这个叫做「**规则即数据**」（Rules-as-Data）。

更进一步——我们设想过一个「规则市场」：玩家社区提交自己的 YAML 规则补丁（比如「骑兵对弓兵加成从 1.3 改为 1.5」），跑自动化平衡测试，通过后合并。光荣《三国志》做了 30 年的数值平衡，开源社区能不能做得更好？
